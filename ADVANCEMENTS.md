<details><summary>How these are detected</summary>

- **Blast Off, Bop** — A thrown Wind Charge deals a point of projectile damage in its burst, so minecraft:player_hurt_entity fires with direct_entity minecraft:wind_charge — exactly the pattern blazeandcave:adventure/from_under_your_feet and blazeandcave:end/unstoppable_force_vs_immovable_object already use. Naming minecraft:wind_charge (not breeze_wind_charge) keeps a Breeze from earning it for you. The knockback itself is not asserted: the explosion applies damage before velocity, so a movement predicate would read the pre-launch value and never match — the launch is a guaranteed consequence of the hit rather than a checked condition.
- **Boat Drop** — minecraft:fall_from_height never fires for a boat passenger (the boat absorbs the fall), so the sampler stays. The dispatch no longer round-trips `on vehicle ... on passengers`, which re-entered the player context once per rider and made the advancement unobtainable with a second person aboard: detect/boat_gate stays as the player throughout and only asks whether the vehicle is a boat, with `execute store result score @s bacaphd_in_boat run execute on vehicle if entity @s[type=#minecraft:boat]`. The store target resolves in the player context before the fork, so the sampler runs exactly once per player. Every 10 ticks a Y sample that drops 4-200 blocks counts as falling, the Y before the first such sample is remembered as the top, and when the descent stops after two or more consecutive falling samples a total of 60+ blocks grants it. bacaphd_bd_seed re-seeds bacaphd_bd_prev on the first sample after boarding, so a stale previous position from before the ride can never be read as a fall, and leaving the boat (including on death) zeroes the sample counter. Unchanged this round.
- **Breeze Block** — One minecraft:player_killed_entity criterion on a breeze, with killing_blow carrying the blazeandcave:spear damage type tag - the same tag and the same field blazeandcave:weaponry/hit_and_run uses to mean 'the charge attack, not a normal swing'. No equipment check is needed because only the charge attack produces that damage type.
- **Bundle of Everything** — Sixteen inventory_changed criteria, one per coloured bundle item, all required by default (requirements_json empty, so the requirement set covers the criteria set exactly). The plain uncoloured minecraft:bundle is deliberately not required, so this is exactly the sixteen dyed variants and does not restate BACAP's animal/humble_bundle.
- **Chamber of Secrets** — Six independent minecraft:player_generates_container_loot criteria, one per Trial Chamber loot table, copying the exact condition shape of Enhanced Discoveries' Bastion Robber ("loot_table": "minecraft:chests/bastion_bridge"). All six table IDs are attested in VALID_IDS.txt as chests/trial_chambers/{entrance,corridor,intersection,intersection_barrel,supply,reward}. requirements_json is empty so the default applies: every criterion is its own group, i.e. all six are required. Each fires the first time that container type generates its loot for this player, and they do not have to be in the same chamber.
- **Estate Sale** — Pure criteria, two of them AND-ed by the default requirements: player_killed_entity on a wandering_trader (BACAP adventure/murderer shape) and a Lead used on a trader_llama (BACAP animal/beeloons shape). The idea asked to TAME the two llamas; taming is not something a Trader Llama supports, so leashing one is the version that is both real and checkable, and the count of two is dropped because criteria cannot count. The order is not enforced by the criteria but is enforced by the game: while the trader lives its llamas are already leashed to it and Mob.canBeLeashed refuses a second holder, so in practice the trader has to die first. Adjacent to ED's Wandering Caravane (leash a boat with the trader and a llama inside), which needs the trader alive.
- **Featherweight** — The kill itself is a plain minecraft:player_killed_entity criterion, and the empty armour and offhand slots are five inverted equipment conditions on that same criterion -- version-proof, and evaluated at the exact instant of the kill. There is no Wither-kill statistic delta line at all, so nothing can collide with batch 3's Pyrrhic Victory. The only thing a function still has to answer is what is in the 36 carried slots, and detect/featherweight does that every 10 ticks for players within 128 blocks of a Wither: exactly one sword (#blazeandcave:swords), exactly one bow, at most one stack of arrows, and an Inventory list length equal to that expected stack count. The result is parked in bacaphd_fw_kit, which the criterion reads with minecraft:entity_scores, and which is zeroed again as soon as no Wither is in range so nothing stale is left on the scoreboard. An unset bacaphd_fw_kit fails entity_scores, so the default is 'not qualified'. Unchanged this round.
- **Fetch Quest** — One minecraft:allay_drop_item_on_block criterion. The condition shape is lifted verbatim from Enhanced Discoveries' Uncontrolled Reproduction: a location_check for the note block plus a match_tool on the dropped stack, which is what the trigger puts in the TOOL slot. The only change is that match_tool asks for count>=64 instead of a specific item, so the allay has to arrive with its single inventory slot completely full. This assumes the trigger reports the whole stack the allay throws rather than one item at a time; that is how the allay empties its container, but it is the one part of this I could not confirm from the reference packs.
- **Free Solo** — Every 10 ticks detect/free_solo does eight cheap block lookups at the player's feet (ladder, vine, both cave vine states, both twisting and both weeping vine states); only if one matches does the NBT position read happen. The accumulator records the Y of the first climbing sample as bacaphd_fs_start and reports NET displacement, bacaphd_fs_y - bacaphd_fs_start, so descending gives back exactly what it took and 2000 decimetres really means two hundred blocks of net ascent. The instant the feet block is not climbable the anchor and the progress are both wiped, and the grant path wipes them too. Creative is excluded because creative flight makes the climb free. Unchanged this round.
- **Golem Foundry** — SUBSTITUTE for 'Terra Incognita' (see report). Detector detect/golem_foundry runs from bucket_slow (every 5 s) for Overworld players who lack it. It counts Villagers within 48 blocks with `execute store result score #gf_villagers bacaphd_gfv if entity @e[type=villager,distance=..48,limit=10]` — a scoreboard count capped at 10, never `if entity @a[limit=N]` — and then requires an `@e[type=iron_golem,distance=..48,limit=1,nbt={PlayerCreated:0b}]`. PlayerCreated is 1b on any Golem a player built from blocks, so 0b is a natural village spawn. Stated plainly: the twenty beds from the original idea text are NOT counted (a bed scan would be a block sweep), which is why the description now only promises 'big enough'. gamemode=!creative is on the bucket line because a creative spawn egg also produces PlayerCreated:0b.
- **Junk Drawer** — One inventory_changed criterion with a bundle_contents item sub-predicate. BACAP's animal/fractal proves the shape `"minecraft:bundle_contents": {"items": <collection predicate>}`; this uses the collection predicate's `size` field instead of `contains`, so it asks for sixty-four separate stacks inside one bundle. A bundle merges identical items into one entry and holds sixty-four weight units, so sixty-four entries can only be sixty-four distinct single items, each of them a normally-64-stackable type. Fires the instant such a bundle is anywhere in the inventory. The only field I could not find already in use in an installed pack is `size`; `contains` and `count` are attested, `size` is the third field of the same record and is what carries the count of entries.
- **Key Master** — `count: {min: 16}` inside an inventory_changed item predicate matches ONE stack of sixteen or more, not a total, so the normal loot-several-vaults result of 8+8 in two stacks failed a description that says 'hold sixteen'. The check therefore lives in bacaphd:detect/key_master, which uses `execute store result score @s <obj> run clear @s <item> 0` — maxCount 0 counts matching items across the entire inventory (including offhand and armour) and removes nothing. bacaphd_okeys is zeroed at the top of the function so a stale value from a previous sample can never grant on its own, and bacaphd_tkeys is overwritten every call.
- **Legend Has It** — Eight independent item_used_on_block criteria, one per banner colour, copied verbatim from BACAP's own 'I'm not lost anymore!' (match_tool filled_map + location_check on the banner block); empty requirements means all eight are needed. The trigger only fires when MapItem.useOn actually toggles a marker, so the banner has to be inside the map's area — the same behaviour the BACAP entry already relies on. Deliberate change from the brief: 'eight different banners on ONE map' is not expressible in criteria (banner markers live in the map's saved data, not on the item), so this counts eight distinct banner COLOURS instead and the description says so.
- **Meals on Wheels** — Four bucket_medium lines, no detection function. Each looks for an item entity of one villager-shareable food (bread, carrot, potato, beetroot) lying within 2 blocks of a Villager and 4-16 blocks from the player, then grants to @p resolved AT THE ITEM. The 4-block stand-off is the discriminator against the player simply dropping bread at their own feet; a player who deliberately throws bread 5 blocks into a crowd of villagers could still cheat it, and I would rather state that than hide it. The gate `if entity @e[type=minecraft:villager,distance=..16,limit=1]` runs first so the item scan costs nothing away from a village.
- **Not Insured** — minecraft:entity_killed_player is the death trigger BACAP already uses (end/the_actual_end, monsters/aww_man), so it definitely fires. The player predicate is a loot-condition list: an any_of that accepts a Totem anywhere in the 36 main inventory slots (container.*, the slot family Enhanced Discoveries already uses) OR anywhere in the Ender Chest, plus two minecraft:inverted terms that reject the run if either hand holds one. The Ender Chest branch is deliberate insurance against the one thing I cannot confirm from the reference packs: whether death drops have already emptied the main inventory by the time the trigger evaluates its predicate. If they have, the container.* branch silently never matches and the Ender Chest branch alone carries the advancement (and the two inverted hand terms pass trivially, so there is no false negative either way).
- **Not My Problem** — Pure bucket lines, no detect function. Every 0.5 s each nearby Iron Golem is hopped through `execute on target`, which tags whatever mob the golem is currently fighting with bacaphd.nmp_mark; a separate line grants the advancement when a marked non-player mob is sitting at Health:0.0f (its 20-tick death animation) with a golem still within 24 blocks. The clean-hands half is a cooldown: a private mirror of minecraft.custom:minecraft.damage_dealt sets bacaphd_nmp_cd to 10 medium-ticks whenever the player deals any damage, and the grant line only fires at cd exactly 0, so you must have dealt no damage at all for five seconds before the kill. Caveat stated plainly: this is 'the golem was fighting it and it died' rather than a real damage-source hook, so a marked mob that dies to fall damage or fire while the golem chases it would also count.
- **Ominous Marathon** — FIXED for sampling lag. The signal is the vanilla minecraft.used:minecraft.ominous_trial_key statistic — actually unlocking an Ominous Vault, and exactly the statistic Enhanced Discoveries' adventure/ominous_vault_hunter is built on, so it is attested. The whole three-line sequence now lives in bucket_fast (every tick) instead of bucket_slow (every 100 ticks): initialise, credit, resync, in that order. That closes the reviewer's hole — at a 5-second sample a player on rockets covers well over 256 blocks between the key being spent and the position being read, so five unlocks inside ONE chamber could each be credited from a different sampled spot. At one tick the sampled position IS the vault the key was just spent on. bacaphd_okey is mirrored into bacaphd_okeyb; a credit fires only on an increase, and the resync runs immediately after the credit in the same tick, so exactly one credit is taken per key spent. The mirror is seeded the first time a player is seen, via the bacaphd.om_init tag, so a lifetime total can never read as a fresh unlock; it is used by nothing else; and the resync line is ungated (`execute as @a run ...`) so no advancement state can desynchronise it. Every credit is checked against ALL previously credited positions (five bacaphd_lx1..lx5 / bacaphd_lz1..lz5 pairs) and rejected unless it is at least 256 blocks away on the X or the Z axis from each of them, so one chamber can never be counted twice no matter how many Ominous Bottles are brought back to it. 256 sits between the width of a single chamber and the 12-chunk minimum structure separation; two chambers closer than that are simply not both counted, which loses the player nothing but a walk and never grants for free.
- **Say It With Flowers** — One stateless bucket_medium line, no function file. Vanilla's OfferFlowerGoal puts a real Poppy into the golem's main hand for the whole 400-tick offer, and that is saved in HandItems, so the line matches @e[type=iron_golem,nbt={HandItems:[{id:"minecraft:poppy"}]}] within 20 blocks of a player who lacks the advancement, then runs `at` the golem and requires a Villager within 5 blocks matching blazeandcave:is_baby (BACAP's own flags:{is_baby:true} predicate, already used 60 times by Enhanced Discoveries in selectors). NBT list matching is subset matching, so it fires whichever hand the poppy is in. Caveat worth stating: it detects the golem holding the flower out with a cub in range, not the cub actually taking it — vanilla never exposes the acceptance event.
- **Spawner Camper** — DETECTOR 1 of 5. The advancement's own in_chamber criterion is the gate: minecraft:location re-fires every 20 ticks while the player stands inside a Trial Chamber, and bucket_fast revokes the criterion again immediately after using it, so the 7x3x7 block probe runs exactly once per second and only for a player who is inside a chamber right now. The probe arms (bacaphd_sc_ok=1, damage mirror seeded in the same two lines) only on a trial_spawner in state waiting_for_players, i.e. before the wave exists, so damage taken mid-wave cannot be washed away by re-arming; bucket_fast clears the flag the moment minecraft.custom:minecraft.damage_taken moves; the grant fires when a spawner within the same box reaches ejecting_reward with the flag still set. Stated plainly: I have NOT been able to confirm the trial_spawner_state value names against a running server here -- waiting_for_players and ejecting_reward are taken from the block-state list and if either is wrong the command fails to parse and detect/sc_z alone stops loading (it is not on a shared tag). Everything else in the batch is unaffected.
- **The Five Stages of Grief** — Five minecraft:effects_changed criteria, the trigger BACAP already uses for adventure/hard_mode_activated (trial_omen) and adventure/war_is_coming (raid_omen amplifier min 4). Each one pins the amplifier to exactly one value with min==max, so Trial Omen V cannot satisfy all five at once and each level really has to be drunk and carried into a chamber. The location gate is the ED shape from bacaped:nether/bastion_sweet_bastion, an entity_properties predicate with location.structure. One deliberate weakening against the idea: I dropped 'the SAME Trial Chamber'. Holding chamber identity needs a stored position and a leave-reset, i.e. a detector, and the budget was better spent elsewhere - the description now says 'inside the Trial Chambers', which is exactly what the criteria check. No requirements block, so all five are required.
- **Wind Rider** — Pure criteria on the SIDEWAYS axis, which no existing advancement measures: minecraft:fall_after_explosion with a wind_charge cause and distance.horizontal.min 80, the same trigger and cause shape BACAP uses in redstone/we_have_liftoff and Enhanced uses in adventure/nobody_needs_rockets, with the horizontal component of the distance predicate that BACAP already uses in minecraft/nether/fast_travel and adventure/sniper_duel. New in this round: a `flags: {is_flying: False}` player condition. distance.horizontal is measured from the latched impulse impact position to wherever the player finally touches down, so without that guard one Wind Charge followed by an ordinary elytra glide accumulated the eighty blocks and the wind did none of the sideways work. `is_flying` is the pack set's attested gliding flag (BACAP ships blazeandcave:predicate/is_flying and uses it in technical/divers_dozen_count alongside an equipped elytra; Enhanced's technical/air_battle_detect writes its 'without using elytra' clause as is_flying:false). A player who was never gliding reads false, so the guard can only ever remove the glide route, never a legitimate grant. Zero functions, zero objectives, no tick cost.
- **Zoom and Enhance** — The `extend` criterion is a vanilla minecraft:recipe_crafted on minecraft:map_extending, exactly the shape BACAP's Mold Maker uses for smithing-template recipes. requirements is AND-of-groups with an impossible guard, so holding `extend` can never complete the advancement on its own; detect/zoom_and_enhance revokes the criterion first (a revoke after the grant would un-complete it), counts one extend, and grants at four - scale 0 to scale 4 is maximum zoom. Two things I am not certain of and have not hidden: recipe_crafted fires from the crafting result slot with the RecipeHolder that produced the item, and I believe special recipes such as minecraft:map_extending carry a holder and fire it, but I could not find a special-recipe example in BACAP to confirm; if that assumption is wrong the criterion simply never fires (recipe_id is a plain resource location, so nothing fails to load). And nothing here ties the four crafts to one Map - four extends of four different Maps also count.

<details><summary>How these are detected</summary>

- **Amphibian Assassin** — DETECTOR 1 of 3. bucket_fast dispatches only for a non-spectator who lacks the advancement AND has a Frog within sixteen blocks, then runs as each slime_ball item entity inside that same sixteen blocks (bounded by distance= and limit=). The function grants only if the item has no Thrower NBT tag and a Frog is within 2.5 blocks: a player-dropped or player-thrown item always carries a Thrower UUID, a mob drop never does, so a slimeball tossed at a Frog's feet cannot claim it. Per-tick rather than per-half-second because a slimeball can be picked up ten ticks after it lands. Honest limitation: a Slime the player kills while standing right next to a Frog would also pass, since both routes produce an un-thrown slimeball beside a Frog.
- **Armadillo Roller** — Every 10 ticks, for non-spectator non-creative players near an Armadillo, bacaphd:detect/armadillo_roller looks for an Armadillo within 8 blocks whose 'state' NBT string is "scared" or "rolling" and increments bacaphd_roll once per roll-up, using bacaphd_roll_lock as a latch so a single long roll cannot count twice. Five distinct roll-ups grant the advancement, and both bacaphd_roll and bacaphd_roll_lock are reset on the grant path (lock first, then the counter, so the second reset's guard still sees the score) so nothing leaks. The 'state' field and its four values idle/rolling/scared/unrolling are now confirmed against Armadillo$ArmadilloState in the 26.1.2 class files, so this is no longer a guess.
- **Bee Movie** — Unchanged this round. Criterion `stung` is entity_hurt_player with the damage source entity a Bee, and `counted` is minecraft:impossible so the criteria never grant on their own. bucket_medium reacts to `stung`, revokes it to re-arm, and only then counts Bees carrying HasStung:1b within six blocks - melee range, executed `at @s` - with limit=20 so the NBT scan is bounded no matter how large the apiary. Twenty of them plus a player whose health objective still reads 1 or more is twenty stings survived.
- **Bless You** — Substitution for the dropped Nosey Parker. One stateless bucket_medium line, no function file: run `as` a Panda within 12 blocks matching blazeandcave:is_baby, then `if entity @e[type=item,distance=..4,nbt={Item:{id:"minecraft:slime_ball"}}]`. It therefore fires the moment the sneeze drop lands beside the cub while you are stood over it; picking it up is then a formality, so it credits the drop rather than the pickup. A slimeball you throw down yourself next to a cub would also count — acceptable cheese for a task.
- **Bombproof** — The only detection function in this batch. The blast criterion is pure entity_hurt_player with an unblocked creeper as the damage source (same damage.source_entity field blazeandcave:monsters/blast_shield uses); the impossible criterion sits in its own AND group so the criterion alone cannot complete it. Every tick bucket_fast picks out players holding blast=true and impossible=false, revokes blast FIRST so the doorbell re-arms, then grants only if @e[type=minecraft:armadillo,distance=..5,limit=1,nbt={state:"scared"}] (or state:"rolling") matches. The armadillo state NBT string is copied from Enhanced Discoveries' Scared Box, which matches nbt "{state: \"scared\"}" on a looked-at armadillo, so the field name and casing are verified rather than guessed.
- **Breakfast in Bed** — DETECTOR 1 of 5. Nothing in the criteria set can see an item entity appear beside a mob, so this one is earned. bacaphd_sleeps mirrors minecraft.custom:minecraft.sleep_in_bed - a criterion BACAP itself already uses - and is seeded in detect/init_b5 from bacaphd:seed BEFORE any bucket runs, so a save's existing sleep count can never be read as one fresh wake. When the mirror moves, detect/bib_wake resyncs it for every player and opens a 40-sample (400-tick) window; inside that window detect/breakfast_in_bed looks for a rabbit's foot, rabbit hide or phantom membrane item entity within 3 blocks OF THE CAT (execute at @e[type=cat,distance=..8,limit=1]), with BACAP's `unless data entity ... Thrower` guard so an item you dropped yourself cannot stand in for the gift. Honest caveat: only a tamed cat gifts, so I do not test the Owner tag - the gift itself is the proof - and I use the three least litter-like of the seven gift items, which costs roughly three extra nights of waiting but removes the false positive of sleeping beside a floor strewn with string and feathers.
- **Bucket Brigade** — Substitute for Interspecies Olympics, which needed ally kill-credit for five different mobs and is not detectable without watching mob deaths. Function-granted. bucket_medium does the cheap test itself - the player must have a Bucket of Tropical Fish in the mainhand - so the detector never runs for anyone not on the job, and two reset lines cover the moment the bucket is put away. The detector requires an Axolotl within 8 blocks on every single sample and accumulates the same octagonal horizontal distance the rest of the pack uses; 2000 decimetres grants, any broken sample resets to zero and re-seeds the previous position. It does not pin the Axolotl's UUID: an unbroken chain of half-second samples each containing one is the same animal in every practical case.
- **Climate Croakers** — Complete redesign - the old 'Frog Chorus' was a strict subset of bacaped:animal/what_are_you_doing_in_my_swamp and needed no function at all. This version is pure criteria: three bred_animals criteria built from blazeandcave:animal/frog_family's own parent/partner shape, each additionally requiring BOTH bred frogs to carry the same minecraft:frog/variant component value (the component form is attested by blazeandcave:biomes/birdkeeper's minecraft:parrot/variant). Requiring both sides removes the ambiguity of which of the two animals the game labels 'parent'. Because a Frog's variant is fixed by the biome its tadpole matured in, this forces the player to actually raise breeding pairs in a warm biome and in a snowy biome, not merely stand near three frogs. No tick function and no scoreboard are involved.
- **Colour Theory** — Substitute for Estate Sale. minecraft:bred_animals carries parent, partner and child predicates; Sheep persist their wool colour as the Color byte, so 11 is blue, 4 yellow and 13 green. The trigger does not promise which of the two animals lands in `parent`, so both orderings are written and OR'd in one requirements group - a single group is an OR, which is what is wanted here and exactly what must never be done around an impossible guard. Constraining the parents as well as the child stops two green Sheep breeding green from counting.
- **Copper Stable** — The anchor for the horse_one_cm delta is re-taken on every ride, so bacaphd_hdiff is distance ridden on THIS horse rather than lifetime horse distance since the player was first seen on a copper-armoured one. Each slow tick the bucket flags every ungranted, non-spectator, non-creative player that currently holds an anchor with bacaphd.cs_off; the detector — reached by walking `on vehicle` to a horse wearing minecraft:copper_horse_armor in armor.body and `on passengers` back to the rider, the hop BACAP itself uses in biomes/submarine_fleet — clears that flag and does the delta work; whoever is still flagged afterwards runs detect/copper_stable_off, which drops the anchor tag so the next mount re-snapshots. The statistic mirror is initialised at mount time (never against zero), belongs to this advancement alone, and its housekeeping is not gated on the advancement state of anyone else. gamemode=!creative is present because this measures distance travelled. The description says 'without dismounting', which is what the mechanism tests: a break of more than one 5-second sample resets the anchor.
- **Duvet Day** — One stateless bucket_medium line, no function file. It runs `as` each Cat within 12 blocks of a player who lacks the advancement, requires `if data entity @s Owner` (tamed — TamableAnimal only writes Owner once tamed) and `if block ~ ~ ~ #minecraft:beds` at the cat's own position: a bed is 0.5625 high, so a cat lying on top floors into the bed block itself. Deliberately NOT gated on nbt={Sitting:1b} — the lying-on-a-bed state is the unsaved DATA_IS_LYING flag, not the Sitting NBT, so testing Sitting would make it unobtainable. Ownership is 'tamed and yours by proximity', not a UUID match against the player, and 'your own bed' is any bed within 12 blocks; both are stated here rather than hidden.
- **Evel Knievel** — Detector detect/camel_dash, per tick from bucket_fast. The bucket line reaches the rider with the same `on vehicle if entity @s[type=camel] on passengers if entity @s[type=player]` chain the existing Copper Stable line uses, so the function only ever runs for someone actually mounted. It reads the Camel's OnGround byte into $ek_air (pre-set to 1, so a failed read can never look like flight). Grounded: it settles the previous leap and re-latches the take-off X/Y/Z. Airborne: it takes max(|dx|,|dz|) from the take-off block and keeps the best value of the leap. The grant needs best >= 7 AND a landing no more than one block below take-off, which is what stands in for 'across a gap' rather than 'off a cliff'. Two honest caveats: positions come from `data get entity @s Pos[n]`, which truncates rather than floors, so a diagonal leap is measured on its longer axis only and can be up to one block out; and the air beneath the span is not inspected. Description reworded from 'Dash a Camel clean across a gap at least seven blocks wide' because the criteria measure the leap, not the gap.
- **Family Planning** — Pure criteria: three bred_animals criteria AND-ed by the default requirements, each pinning both parents to minecraft:chicken (parent/partner in BACAP's animal/billy_the_kid shape) and the player's own location to one dimension (dimension field in BACAP's end/extrabiologist shape). Pinning the species is what makes it 'the same species everywhere' — criteria cannot correlate with each other, so an unpinned version would have allowed cows here and pigs there — and Chickens are the one species you can ferry without a lead or a boat, by throwing Eggs in the far dimension and waiting for the chicks to grow. Chicken variants (cold/warm) are components on minecraft:chicken, not separate entity types, so all of them count. Deliberately narrower than this pack's challenges/the_long_haul, which is ten species and Nether-only and never touches the End.
- **Full Kennel** — Ten player_interacted_with_entity criteria copy blazeandcave:animal/paw_patrol's proven structure exactly, using the ten dye colours Paw Patrol leaves out, so each fires when you equip a Wolf with Wolf Armor of that dyed_color integer. The eleventh criterion 'kennel' is impossible and is granted by bacaphd:detect/full_kennel, which counts only Wolves actually WEARING Wolf Armor (nbt={equipment:{body:{id:"minecraft:wolf_armor"}}}). The 'equipment' compound and its 'body' slot key are confirmed against LivingEntity and EquipmentSlot in the 26.1.2 class files, so wild unarmoured wolves cannot pad the count. The description promises only what is enforced: ten colours equipped over time, ten armoured Wolves gathered at once.
- **Hatchling** — Function-granted (the one detection function this batch is allowed). bucket_fast runs every tick for players who lack it; bacaphd:detect/hatchling samples each chicken within 32 blocks exactly once ever (bacaphd.hatch is permanent) and reads its Age into a score. A chick spawned by a hatching egg is at the vanilla baby spawn value of -24000 and gains 1 per tick, so the -24000..-23995 window only ever admits chickens born in the last five ticks - chicks the player merely walks up to aged past it long ago. Each such newborn then counts how many other newborns stand within 2 blocks using `execute store result ... if entity` (never `if entity @e[limit=4]`, which would succeed on one), and the largest cluster of the tick is compared against 4. Natural chicken group spawns are adults with Age 0 and are excluded by the window; two eggs would have to hatch within five ticks of each other and land within two blocks to false-positive. I am asserting from the vanilla baby spawn age that a hatched chick is created with Age -24000; if a future version changed that constant the window would need moving, and nothing else here would break.
- **Herding Cats** — Renamed away from BACAP's 'Crazy Cat Lady' and rebuilt so the variants really are the point. The advancement carries a single impossible criterion (the captain_america pattern) and is granted by bacaphd:detect/herding_cats, which chains eleven separate 'if entity @e[type=minecraft:cat,nbt={variant:"minecraft:<v>"},distance=..8,limit=1]' probes - the same nbt={variant:...} entity form Enhanced Discoveries ships in what_are_you_doing_in_my_swamp_check.mcfunction. The NBT key is confirmed: VariantUtils.TAG_VARIANT is the string "variant" and Cat writes its variant through it in 26.1.2, and the eleven ids match data/minecraft/cat_variant/ exactly. Eleven bred copies of one variant no longer pass.
- **Parrot Choir** — Five tame_animal criteria copy blazeandcave:biomes/birdkeeper exactly, one per minecraft:parrot/variant value, so the colours are handled natively. The sixth criterion 'choir' is impossible and is granted by bacaphd:detect/parrot_choir. Parrot.tick only dances a Parrot while the Jukebox BlockPos is closerToCenterThan(pos, 3.46) - I read that constant out of the 26.1.2 Parrot class - so the five are now counted from the Jukebox, not from the player: each probe that finds a jukebox[has_record=true] in the 3x3 column at or one below the player's feet snaps to that block's centre with 'align xyz positioned ~0.5 ~0.5 ~0.5' and calls detect/parrot_choir_count, which counts @e[type=minecraft:parrot,distance=..3] from there. A Parrot five blocks from the player but six from the Jukebox can no longer pad the choir. The cheap outer gate was widened from 5 to 8 blocks so a legitimate Parrot on the far side of the Jukebox is not missed, and #h5_jukebox still short-circuits the scan with a single grant at the end.
- **Parrot-phrase** — Substitution for the dropped Silent Running. One stateless bucket_medium line, no function file: `as` a Parrot within 8 blocks of the player, `if data entity @s Owner` (tamed), `if entity @e[type=#blazeandcave:hostile_monsters,distance=..20,limit=1]`. Twenty blocks is vanilla's own imitation radius, so this is exactly the state in which a parrot starts mimicking — but the mimic call itself is a client sound with no server-side hook, so the advancement fires on the setup, typically a second or two before the first squawk rather than on it.
- **Selective Breeding** — Nine independent minecraft:bred_animals criteria, one per species-variant pair, each testing the newborn through the trigger's `child` entity predicate. requirements_json is empty so the default AND-of-all applies and every criterion name is covered exactly once. The `child` shape with a raw entity predicate is copied from BACAP animal/bunny_lover; the `components` variant form is copied from BACAP biomes/birdkeeper (`minecraft:parrot/variant`) and Enhanced Discoveries nether/the_new_swamp_wont_be_here (`minecraft:frog/variant`), and `minecraft:cow/variant`, `minecraft:pig/variant`, `minecraft:chicken/variant` are all attested in VALID_IDS.txt with `temperate`/`warm`/`cold`. The calf, piglet or chick inherits its variant from a parent, so the player has to take breeding pairs to (or from) all three climate bands rather than just breeding at home.
- **Shake It Off** — Detector 1 of 5. Every ten ticks, wolves within sixteen blocks whose feet are in a minecraft:water block get tagged bacaphd.sio_wet; a tagged wolf next seen out of water and OnGround is shaking itself off, and the grant hops `on owner` to its tamer, filtered by the bacaphd.sio_self tag so a bystander cannot be granted for someone else's dog. `on owner` resolves to no entity for an untamed wolf, which is what enforces 'tamed'. Caveat I am flagging rather than hiding: there is no NBT flag for the shake animation itself, so this detects the water-to-land transition that always causes it, not the animation. `on owner` is the same execute sub-command family as the `on vehicle` / `on passengers` hops HD's Copper Stable and Ghast Couture already use, but it does not itself appear anywhere in the corpus.
- **Sticky Fingers** — Pure criteria, exactly BACAP's animal/foxy_thievery shape (thrown_item_picked_up_by_entity, item predicate, fox entity condition) with the Totem swapped for a Diamond. The trigger fires from LivingEntity.onItemPickup for the ItemEntity's owner, so it only counts an item YOU dropped, and a Fox with an empty main hand will pick up any ground item it can reach. The item is pinned to a Diamond on purpose: an unrestricted 'any item' version would be strictly dominated by Foxy Thievery and by ED's Flint and Steal and would fire as a side effect of both. Nothing else in the three packs asks a Fox to hold a Diamond, so it neither dominates nor is dominated.
- **Storm Warning** — One player_interacted_with_entity criterion: feeding bamboo to a panda whose MainGene is "worried" (the NBT form BACAP's Pandamonium uses; worried is a dominant gene so MainGene alone settles it) while minecraft:weather_check reports thundering — the exact condition that makes a worried panda cover its face, and the same weather_check shape Enhanced Discoveries uses in Frozen Heart. Changed from the brief's passive 'stand beside it', which would have needed a detector: there is no criterion for merely standing near a mob, so the player has to make one interaction while the scene is happening.

The five indices are then counted for distinct non-zero values and three or more grants. Exact, not tag-approximated: two different forests count as two different biomes.

One minecraft:location criterion (which the server re-evaluates every 20 ticks) carrying four minecraft:any_of groups, one per protection type, each ranging over head/chest/legs/feet. Because the four protection enchantments are mutually exclusive on a single item, satisfying all four groups AT THE SAME MOMENT is only possible with four different worn pieces -- so the 4! orderings collapse into one criterion instead of 24. Spectators are excluded with the same inverted gamemode term BACAP uses. One criterion, no requirements block, so the default (all criteria) applies.

- **Death by a Thousand Cuts** — Pure criteria, no tick cost. The damage source predicate has no field for a specific damage type ID - only tags - so thorns is isolated by shape instead: the killing blow's direct entity is the PLAYER (vanilla builds thorns damage as damageSources().thorns(wearer), which puts the wearer in both the direct and causing slots) while every tag that a real player hit would carry is required false. Melee, mace smash, arrows and tridents, explosions, fire and fall are all excluded, and potions, wind charges, fireworks and pets all set direct_entity to the projectile or the pet - leaving thorns as the only way a player-direct killing blow reaches a Ravager. The mace_smash tag is used exactly as BACAP uses it in enchanting/over_overkill; if that tag did not exist the expected:false test still passes, so it cannot break the criterion. - **Deep Impact** — SUBSTITUTION. This replaces the batch's 'Grass Fed' (shear a Sheep, let its wool regrow, shear the same Sheep again). That needs the sheared sheep's identity remembered across its Sheared flag flipping back to 0, which is per-entity state and therefore a detection function; detector_allowance is 0, so it was swapped for this spare.

MECHANISM. One minecraft:entity_hurt_player criterion, so the default requirement set covers it exactly. damage.type.tags requires minecraft:is_fall; damage.taken requires at least 20.0; and the player predicate requires the feet slot to hold Feather Falling IV. Single criterion, no OR group, no impossible guard.

WHAT I VERIFIED, not from memory. minecraft:is_fall is attested in Enhanced Discoveries animal/driven_to_death, which uses that exact tag id on a killing_blow for a rabbit that died from a fall. The equipment/predicates/enchantments shape is verbatim from BACAP enchanting/silent_but_deadly (Swift Sneak III on legs), with legs swapped for feet and the enchantment id swapped. minecraft:feather_falling, minecraft:diamond_boots and minecraft:enchantment_glint_override are all in VALID_IDS.txt (the enchantment id is registry-checked because verify.py skips 'enchantment', not 'enchantments'). The trigger is on the attested list. Parent blazeandcave:enchanting/like_a_cat ('Obtain boots enchanted with Feather Falling') is in PARENT_CANDIDATES.md and is the direct thematic parent.

HONEST DEVIATION. The spare asked for a DEATH, and there is no vanilla path to a sourceless death. minecraft:entity_killed_player only receives a killer entity — every use of it in BACAP (challenges/death_from_all, 52 criteria, all mob types) and in Enhanced Discoveries names a mob — and fall damage has no entity, so it can never reach that trigger. What is checked instead is the damage. 'taken' is the amount actually applied after armour, Protection and Feather Falling, so 20.0 is a full vanilla health bar: the landing is fatal for any player at normal health without Absorption or Health Boost. With Feather Falling IV removing 48%, 20 taken means roughly 38 raw damage, about a 41-block fall. The description was reworded to state what is measured rather than to promise a death that the criterion does not check. I rejected minecraft:fall_from_height (attested, used by ED mining/the_master_of_falls) because it measures distance fallen, not damage suffered, and would not tie the feat to the enchantment failing.

OTHER CAVEATS. minecraft:is_fall also covers stalagmite and ender-pearl damage; ender pearl caps at 5 and cannot reach the threshold, but a 20-damage stalagmite landing would qualify. And this fires on the tick the player dies, so the reward function runs at death — normal for BACAP (monsters/aww_man grants when a creeper kills you).

WHAT I COULD NOT CONFIRM. That minecraft:entity_hurt_player fires on the LETHAL blow. It is invoked from the player's damage path rather than the death path, so it should, but no advancement in either installed pack uses it for a fatal hit and I had no server to test on. If it turns out not to fire on the killing blow, this becomes unobtainable rather than wrong.
- **Desert Diver** — One minecraft:location criterion, which the game re-evaluates for every player about once a second. The player predicate carries the biome and both equipment slots at once: the helmet must hold Aqua Affinity and Respiration III, the boots Depth Strider III. Structurally identical to blazeandcave:enchanting/silent_but_deadly, including its inverted spectator guard. No function needed - the equipment predicate does all the work people usually reach for a detector to do.
- **Dewey Decimal** — One minecraft:inventory_changed criterion carrying sixteen item predicates, so all sixteen must be satisfied by the SAME inventory snapshot - that is what makes it 'at once', where sixteen separate criteria would each be remembered independently. Vanilla's InventoryChangeTrigger walks the inventory and removes a predicate as soon as a stack matches it, so one stack can only ever satisfy one predicate: sixteen distinct Enchanted Book stacks are genuinely required. Deliberate narrowing worth stating: the set of sixteen is fixed (protection, fire_protection, feather_falling, blast_protection, projectile_protection, respiration, aqua_affinity, thorns, depth_strider, sharpness, smite, bane_of_arthropods, knockback, fire_aspect, looting, efficiency) rather than 'any sixteen distinct', because a criterion cannot express distinctness over an open set. All sixteen are ordinary enchanting-table enchantments, no treasure-only ones. Predicate shape copied from blazeandcave:enchanting/complete_enchanter.
- **Disenchanted** — REDESIGNED again. The previous version demanded that the Enchanted Book count fall and the plain Book count rise inside the SAME half-second sample, which a Grindstone can never produce: while the book sits in the Grindstone's input slot it lives in the menu container, invisible to inventory.*, hotbar.* and weapon.offhand, so the drop and the rise are always two separate clicks. It is now anchored to the vanilla statistic minecraft.custom:minecraft.interact_with_grindstone, mirrored as bacaphd_grind. Opening a Grindstone bumps that statistic, which arms a sixty-sample (thirty second) window and snapshots the two book counts as they stood one sample BEFORE the menu opened - the previous sample, so a player who opens and inserts inside the same half second still gets a clean baseline. Anywhere inside that window, Enchanted Books below the snapshot AND plain Books above it grants it. A Grindstone is now an actual condition rather than a word in the description, nothing latches (no window, no grant), and any pacing of the two clicks works. bacaphd_gr_prev is seeded from the player's lifetime total by detect/init_b4 and the bucket line refuses to run until that has happened, so an existing save's Grindstone history cannot arm a window on the first tick. The Mending wording stays dropped: pinning the enchantment needs an item-component sub-predicate that is not attested in either reference pack.
- **Fortune Favours the Melon** — minecraft:inventory_changed with a count range (BACAP uses the same `items`/`count` shape in the anvil-hoarding advancements) and a mainhand equipment predicate combining an item list with the `predicates.enchantments` sub-predicate exactly as BACAP's nether/ludicrous_speed does for boots. The trigger fires on the very stack change the melon break produces, and the mainhand is the axe that caused it. I reworded the description on purpose: a melon caps at 9 slices even with Fortune III, so 'more than nine slices' from ONE break is impossible; what the criterion actually measures is holding a stack of 10+ while swinging the Fortune III axe, which takes two melons. Saying 'break Melons ... until you are holding' is what the check really does. Fortune on an axe is otherwise useless, which is the joke and is untouched by master_axeman.

Each entry must be satisfied by some item in the inventory. Density and Breach both live in the vanilla damage exclusive set, so no single Mace can carry both - the two entries are forced onto two separate Maces, which is the whole joke. Both enchantment IDs were checked against VALID_IDS.txt (V and IV are their respective maxima).

Stated plainly: scraping wax off waxed_weathered_copper or waxed_exposed_copper produces the same result blocks, so a player with waxed copper could satisfy two of the three criteria by de-waxing instead of de-oxidizing; oxidation stage is a separate block ID, not a block state, so no predicate can tell the two apart.
- **Torchbearer** — The scoreboard objective bacaphd_ctorch tracks minecraft.used:minecraft.copper_torch, which vanilla increments each time the BlockItem is placed. The slow bucket grants directly to any player whose score reaches 64. The selector carries gamemode=!spectator AND gamemode=!creative, because this measures block placement and creative torches are free. This is a counting task, not a restatement of BACAP's building/chartreuse (one-off 'light up the area').
- **Urban Decay** — Detector 4 of 5, hybrid with criteria. The `city` criterion is a plain minecraft:location structure test on minecraft:ancient_city with BACAP's inverted-spectator guard; the impossible criterion sits in its OWN requirements group (an AND, never one group containing both) so criteria alone can never complete it. The bucket line selects on advancements={...={city=true,impossible=false}}, so the detector runs only while the player stands in a city and stops the instant the whole advancement is granted. It revokes `city` to re-arm, then credits the site only if it is 512+ blocks (Chebyshev) from BOTH previously credited cities, so shuttling between two cannot pay for a third. The branch is taken on bacaphd_ud_p, a snapshot of the count, so one visit can never advance two states.
- **Vein Miner** — Unchanged this round. Function-granted. bucket_slow fires when either minecraft.mined:minecraft.diamond_ore or minecraft.mined:minecraft.deepslate_diamond_ore changes; detect/vein_miner consumes both deltas on every visit, then adds them to the running count. The window is stamped from the FIRST ore of the run in bacaphd_vein_start, so nine ores fifty-nine seconds apart no longer accumulate; a run whose first ore is more than 1200 game ticks old is discarded and the next ore starts a fresh one. Ore broken in creative is thrown away and ends the run. The count is reset on the grant path.
- **Vertical Limit** — Two medium-bucket lines. Standing in the overworld bedrock layer (`positioned ~ -64 ~ if entity @s[dx=0,dy=6,dz=0]`) arms a 120-sample timer; detect/vl_top then decrements that timer once per 10 ticks and reads the exact altitude, granting at y>=319, so the run expires after exactly 60 seconds. The top test is no longer a selector volume. A dx/dy/dz selector box matches on bounding-box INTERSECTION, not on the feet position, so `positioned ~ 319 ~ if entity @s[dy=2000]` passed as soon as the player's head crossed 319, i.e. with the feet at about y 317.2 -- almost two blocks early. detect/vl_top now stores Pos[1] with scale 1 and compares the score, which is exact. The reviewer's stated cause (Vec3Argument centre-correcting the integer) is not the reason: WorldCoordinates.parseDouble passes centerCorrect=false for the Y component specifically, which is why /tp @s 0 64 0 lands you at 0.5, 64.0, 0.5 -- the Y anchor was already 319.0 and -64.0 exactly. The bedrock arming line keeps the volume idiom: the same intersection slack there only widens the arming zone to feet between about -65.8 and -57, which is the bedrock layer plus a block, and being generous at the START of a 380-block climb costs nothing. No dimension check is needed beyond the overworld guard on the arming line since y>=319 is unreachable in the Nether or the End. Creative is excluded alongside spectator, and the timer is zeroed on the grant path.
- **Weathering Heights** — DETECTOR 4 of 5. Adjacency of four specific blocks has no criterion. detect/weathering_heights scans 11 x 5 x 11 around the player and each position only ever asks whether it is the START of a four-block run, so all but a handful of positions fail on the first `if block` and cost one test. Four chains per position cover both axes and both reading directions, so the gradient does not have to face any particular way. It grants on bacaphd_whh >= 1 and runs at bucket_slow behind @r, so at most one player pays for it per five-second cycle. Waxed variants deliberately do not count: waxing is what stops the oxidation this advancement is about, and Sly Copper already rewards the waxed set.
- **Worked to the Bone** — Pure criteria, one criterion. minecraft:item_durability_changed with `durability: {max: 0}` — verbatim the shape BACAP uses in mining/rest_in_pickaxes (diamond pickaxe) and mining/bling_bling_gone (golden pickaxe). It is an event, not a lifetime statistic, so nobody is granted it on login. Noted for the record: the batch's duplicate check missed that BACAP's mining/moar_broken_tools already carries a copper_pickaxe criterion inside its break-everything collection, and mining/aww_it_broke covers any first tool. This is not a restatement of either — a per-material single-tool break is an established BACAP family (rest_in_pickaxes, bling_bling_gone, fool_me_twice) and copper is the one tier that family does not yet have.

</details>

<details><summary>How these are detected</summary>

- **Bad Medicine** — One effects_changed criterion. The effects map is checked against the player's whole current effect set, so it only passes when all three are running at once, and the source list (the same shape BACAP uses in 'Thanks a lotl') pins the effect that completed the set to a witch. A witch throws Slowness beyond 8 blocks, Poison above 8 health and Weakness at close range, so all three together is a real fight, not a lucky tick.
- **Caught in My Own Web** — enter_block on minecraft:cobweb - the same trigger BACAP redstone/tripping_over uses on tripwire, another walk-through block - with an entity_properties condition requiring minecraft:weaving on the player, matching the `effects` map BACAP potion/marine_marauder uses. Reworded from the original 'a Cobweb that your own Weaving effect spun': Weaving only spawns cobwebs when the affected entity dies, so a player could never both spin the web and then walk into it while still holding the effect. What is checked is the achievable half - being the one wearing Weaving while inside a web - which needs an Ominous-source Weaving on yourself rather than on a mob, and nothing in the four packs covers that.
- **Cell Block** — Function-granted. bucket_slow picks at most one candidate player per five-second cycle with @r, tags the twelve two-block-tall hostiles within 12 blocks, then tests the nearest one's cell: four walls at foot level, four at head level, a floor and a ceiling. Each face is one execute with eight chained `unless block` clauses - one per Copper Bar oxidation stage, waxed and unwaxed - so a face that is any kind of Copper Bar leaves the fail flag alone. The flag starts at 1 and is only cleared once a candidate mob is confirmed to exist, so an empty scan can never grant.
- **Death by Committee** — Unchanged this round. Ten entity_hurt_player criteria (blocked:false, so shield hits do not count) plus an eleventh, `armed`, which fires on damage from ANY entity - source_entity present but empty. All eleven are required and `armed` is implied by every one of the ten, so it costs the player nothing. The first time `armed` shows up, detect/committee_arm starts a fixed thirty second countdown (60 medium ticks) and detect/committee_tick revokes the whole advancement's progress when it runs out; nothing refreshes it. A separate bucket line fires detect/committee_reset the moment the health objective reads 0, so 'and survive' is enforced. Every line that can revoke is gated on advancements={...=false} and committee_arm parks the timer at -1 once the advancement is held.
- **Door to Door** — Detection function bacaphd:detect/door_to_door from bucket_medium. There is no `execute if difficulty`, so the Hard gate is the Zombie's own CanBreakDoors NBT byte, which vanilla only sets on Hard — the exact flag that permits the behaviour. Each door-breaking Zombie's four horizontal neighbours are checked against #minecraft:wooden_doors and a minecraft:marker is dropped in that block (one per block, guarded by `unless entity @e[...,distance=..0.9]`). When a marked block is no longer a door and a CanBreakDoors Zombie is still within 3 blocks, the watching player is granted and the marker is killed. An ungated bucket_slow line kills any marker with no breaker left within 4 blocks, so markers cannot accumulate even after the advancement is held. False positive worth naming: breaking that same door yourself while the Zombie is still on it would also fire.
- **Identity Crisis** — The exact inverse of blazeandcave:monsters/camouflage, built from the same two pieces: minecraft:entity_killed_player (BACAP uses it in monsters/aww_man, where `entity` is the killer) plus a `player` entity predicate carrying equipment.head, the object form BACAP uses in monsters/lancelot. Five head/killer pairs, requirements a single OR group so any one pair completes it. The trigger fires from ServerPlayer.die() before the inventory is dropped, so the worn head is still there when the predicate runs. The piglin pair is included for completeness but is close to unusable in practice - wearing a piglin head pacifies piglins - so the real routes are the creeper head (charged-creeper kill first), zombie head, skeleton skull and wither skeleton skull.
- **Landscape Gardener** — Function-granted, sharing detect/mob_carry_watch with Reverse Logistics. Endermen within 24 blocks that have a carriedBlockState get tagged bacaphd.lg_carry; on a later sample a tagged Enderman with no carriedBlockState has just put its block down, and the player watching gets the grant. carriedBlockState is only written while the Enderman is actually carrying, which is what BACAP's monsters/basketblock_championship keys its own entity NBT predicate off. The pick-up half is implied rather than separately proven: the tag is only ever applied to an Enderman inside the player's 24-block radius, so the player was there while it was carrying.
- **Leaving a Mess** — Pure criteria. minecraft:entity_killed_player with a player predicate requiring the Oozing effect to be active at the moment of death; the two slimes are what the effect does on death, so no separate check is wanted or possible. entity_killed_player needs a killing MOB, so drowning or falling with Oozing does not count -- which matches 'leave a pair of slimes behind you' in a fight. The empty-effect-object form {"minecraft:oozing":{}} is the one already used in bacaphd:challenges/naked_and_afraid.
- **Overtime** — Pure criteria: a pickaxe losing durability while the player holds Mining Fatigue at amplifier 2, which only an Elder Guardian hands out. The effects/amplifier form is BACAP's Maximum Resistance, the item_durability_changed form is Some Breakthrough. There is no vanilla block-broken trigger, so tool damage is the stand-in, and it does not distinguish mining from hitting something with the pickaxe - the gate that actually costs the player anything is holding Mining Fatigue III at all.
- **Pacifist Streak** — A bacaphd_kills objective on the vanilla `totalKillCount` criterion is compared against its own private mirror every 100 ticks; unchanged adds 100 ticks to the streak, any change wipes it, and 120000 ticks (five in-game days of online time) grants it. detect/init_b2 seeds the mirror from the live statistic on the player's first tick so a lifetime kill count is never read as a fresh kill. The whole check is four scoreboard commands per player per five seconds and touches no NBT; the streak is zeroed on the grant path. Unchanged this round.
- **Pyrrhic Victory** — Unchanged this round. Function-granted. bucket_fast watches the minecraft.killed:minecraft.wither statistic against bacaphd_wither_seen_pv - a mirror owned by THIS advancement alone, so it can neither consume nor be consumed by any other Wither-watching check in the pack. The tick a Wither kill is credited, detect/pyrrhic_victory grants if the health objective reads 0, i.e. the player is already dead at that instant. The mirror is rebased on every visit and the housekeeping line is not gated on the advancement, so a lifetime total can never bank up.
- **Rain Check** — Substitute for Possum Impression, which needed an Axolotl's play-dead state and that state is not written to entity NBT, so no detector could see it. This one is pure criteria: minecraft:player_hurt_entity where the victim is an Enderman and the direct damage entity is a thrown minecraft:splash_potion - the entity type, confirmed as an entity id by Enhanced Discoveries' adventure/water_dependent, which matches looking_at against it. Water is the only splash potion that hurts an Enderman without also being a kill in one throw, and any damage at all makes an Enderman teleport, so the hurt event and the escape are the same instant. Damage-type tags are left off on purpose; the projectile identity is the specific part.
- **Skin Crawler** — entity_hurt_player with damage.source_entity typed as a Silverfish - the same damage/source_entity structure BACAP's 'The Nether's Shield' uses - plus an effects predicate on the player (the form ED's wear_dragon_vs_warden predicate uses) requiring minecraft:infested to still be active. That is what ties the bite to the effect's own spawn rather than to a silverfish out of a stone block: Infested outlasts the damage tick that spawned the swarm, so the retaliation lands inside it.
- **Sniffed Out** — One bucket_medium line, no detection function. `execute as <player> at @s as @e[type=minecraft:warden,distance=..24] on target unless entity @s[type=minecraft:player] run advancement grant @p[distance=..1] ...`. `on target` reads the Warden's live attack target and yields no executor at all when it has none, so the guard is exact rather than inferred. `on` moves the executor but never the position, so the grant selector still resolves at the player's own coordinates - @p[distance=..1] is that player and nobody else.
- **Staring Contest** — One polled minecraft:location criterion carrying two things at once: an equipment.head item test (the shape ED uses in bacaped:nether/bastion_sweet_bastion) and the type_specific/player looking_at predicate with an absolute distance cap, copied field-for-field from BACAP's monsters/look_out. The location trigger polls roughly once a second, so the stare has to be held for about a second rather than flicked past - which is the whole point, since the pumpkin is what stops the Enderman aggroing while you do it. The 16-block cap keeps it a stare-down rather than a long-range spot.
- **Terraforming Service** — bucket_medium gates on one Enderman being in range at all, then detect/terraforming_service counts properly with `execute store result score ... if entity @e[...limit=3]` rather than `if entity @e[limit=3]`, which would only test for at least one. Carrying is detected by the presence of the carried block NBT key, matched with an empty compound so any block value passes. Both spellings are counted and summed - carried_block_state (current) and carriedBlockState (pre-1.21.5) - because an Enderman can only ever hold one of the two, so nothing is double counted and the check survives whichever name this server writes. Not confident about which spelling this exact version uses, which is precisely why both are read.

<details><summary>How these are detected</summary>

- **Backdraft** — Two criteria ANDed as two separate requirement groups: placing a bed in the_nether (placed_block + location_check with block and dimension, the shape BACAP's 'Hot Chocolate' uses) and taking explosion damage in the_nether (entity_hurt_player with damage.type.tags is_explosion, the shape ED uses for its void death). Clicking the bed itself is untestable because the block is removed before the trigger reads the position.
- **Bed Bath and Beyond** — Pure criteria: unblocked explosion damage taken inside minecraft:bastion_remnant. damage.type.tags is Dimension Penetration's shape and location.structures is From Whence It Came!'s. Two honest caveats. The damage-type predicate only exposes tags, not a type id, so any explosion inside a bastion qualifies - in practice a bed or a respawn anchor, since creepers do not spawn in the Nether, though a stray Ghast fireball would also do it. And entity_hurt_player fires on the damage tick whether or not the blast kills you, so 'live through it' is flavour rather than something the criterion enforces.
- **Colour Coordinated** — Sixteen minecraft:tick criteria, one per colour, in a single OR requirements group that covers all sixteen names exactly - the player only has to match one colour. Each criterion asks, on the tick, that the player's four leather armour slots all carry the exact `minecraft:dyed_color` integer for that dye AND that their vehicle is a Happy Ghast whose body slot holds the same-coloured harness. The sixteen integers are not computed, they are lifted straight out of BACAP animal/shoe_shed, which asserts them as the result of dyeing a leather item with one dye of that colour. The tick trigger with a `player` list-of-conditions is Enhanced Discoveries adventure/water_dependent; equipment slot keys head/chest/legs/feet/body and `vehicle` are all attested in BACAP advancements (weaponry/hit_and_run uses `vehicle`, predicate/equipment/*.json uses `body`). Because `components` is an exact match, armour dyed twice or with mixed dyes will not qualify - that is intentional, the point is a clean single-dye match.
- **Fortress of Solitude** — The structure test is done by vanilla, not by a function: `inside` is an ordinary minecraft:location criterion whose predicate names minecraft:fortress, copying BACAP nether/midport_village's shape including its spectator exclusion. The game re-evaluates the location trigger for every player every 20 ticks, so detect/fortress_of_solitude revokes that one criterion on every 100-tick sample and finding it back on the next sample proves the player never left. 240 unbroken samples is 24000 ticks — one Minecraft day — and any sample that finds it absent resets the counter to zero. The `impossible` guard is in its own requirements group so the location criterion can never complete the advancement on its own.
- **Fungus Among Us** — No detection function: two bucket_fast lines following the pack's established Ominous Marathon mirror pattern. Placing a block increments minecraft.used: for its item, so bacaphd_wfung (minecraft.used:minecraft.warped_fungus) moving on a given tick means the fungus went down on that tick; the credit is taken there and then, with a hoglin required within eight blocks - a Hoglin's warped-fungus flee radius - reading the player's position at the instant of the placement. The resync line runs ungated for every player so no advancement state can desynchronise the mirror, and it runs after the credit so exactly one credit is taken per placement. The mirror is seeded in seed_lines before the first read. Caveat: minecraft.used:minecraft.warped_fungus also moves when warped fungus is used on a Strider, so feeding a Strider with a Hoglin standing eight blocks away would also pass.
- **Ghast Couture** — FIXED for ownership. The colour tags still live on the ghast so they survive relogs, but two things changed. (1) The tag pass no longer runs for anyone standing near a ghast; it only runs for a player who is RIDING it, reached with `on vehicle` — the same hop BACAP uses in biomes/submarine_fleet. A Happy Ghast can only be ridden once a Harness has been fitted (BACAP's nether/hot_air_balloon: 'Craft a Harness, place it on a Happy Ghast, and ride it'), so 'ridden while it wore this colour' is a faithful stand-in for 'fitted with this colour' and costs the player nothing they were not already doing. (2) The grant is gated on bacaphd.h_new, a marker the tag pass sets only when the colour worn this sample is one the ghast has never worn before. So the grant belongs to the rider who registered the sixteenth colour; a second player who mounts the finished ghast registers no new colour and is not granted. The player's identity is carried across the `on vehicle` hop by the short-lived bacaphd.gc_self tag, because after `on vehicle` the executor is the ghast — going back with `on passengers` would have granted every passenger, up to four people. A body slot holds exactly one item, so at most one colour can match per pass, which is what makes the newness marker exact. `if items entity @s armor.body *` is used rather than a guessed `#minecraft:harnesses` tag; `body` is the equipment slot BACAP reads for Nautilus and Horse armour in blazeandcave:predicate/equipment/.
- **Ghast Nursery** — DETECTOR. A Ghastling is a baby minecraft:happy_ghast - BACAP nether/snow_cone identifies it exactly that way, with flags.is_baby. Every 0.5 s a player who lacks the advancement and has a Snowball in the main hand (`if items entity @s weapon.mainhand`, already used in this pack's bucket_slow) counts happy_ghasts within 8 blocks; each one's Age NBT is read into a score and only negative ages - babies - are counted, so adults are excluded. Three or more grants. The Snowball requirement is in the description because it is genuinely part of the test, and it is also what bounds the cost: without it the entity count would run for every player every half second.
- **Growing Pains** — Pure criteria - this is the one place I abandoned the suggested function. Three AND-groups: place a waterlogged Dried Ghast (the exact placed_block + block_state_property shape of vanilla husbandry/place_dried_ghast_in_water), feed a snowball to a Happy Ghast whose entity predicate has flags.is_baby true (a Ghastling), and fit any of the sixteen Harnesses on a Happy Ghast with flags.is_baby false - which only an adult accepts. The 16 harness criteria are ONE OR-group, so the third group is a single genuine step. Honest limitation: the criteria cannot bind all three legs to the same individual ghast, which the function version would have. In practice a solo player rearing one ghast does exactly this sequence, and I judged that worth trading against a fourth detector.
- **Hunting Party** — SUBSTITUTE for 'Equal Opportunity Offender' (see report). Detector detect/hunting_party, per tick from bucket_fast because a Hoglin's DeathTime reads 1 for exactly one tick and cannot be sampled slower. It counts Piglins with `store result ... if entity @e[type=piglin,distance=..16,limit=3]`, then walks `as @e[type=hoglin,distance=..16,limit=1,nbt={DeathTime:1s}] on attacker if entity @s[type=piglin]`. `on attacker` resolves to the entity that last damaged the Hoglin, so it both proves the Piglins made the kill and rules out the player claiming their own — no kill-statistic mirror and therefore no seeding hazard at all. The player is tagged bacaphd.hp_here for the two lines it takes to get the grant back out of the Hoglin's execution context, and untagged again immediately. DeathTime is a short, hence `1s`; an int literal would silently never match. The 'dance over the kill' half of the original idea is dropped — Piglin celebration is not exposed in NBT — and the description was reworded accordingly.
- **Magma Marathon** — FIXED for the same reason the reviewer raised against Dragon Rider: the description promises 'without taking a single point of damage' and the counter was merely PAUSING on damage, not clearing. bacaphd_lava is now zeroed the moment minecraft.custom:minecraft.damage_taken moves, so the five hundred blocks really do have to be unbroken. Every 10 ticks the medium bucket samples X/Z in decimetres; if the feet block is lava and the damage mirror has not moved since the previous sample, the horizontal step is added to bacaphd_lava. The damage mirror bacaphd_mm_dmg is private to this advancement and is seeded from the player's current lifetime total by detect/init_b4 on first sight, and the bucket line refuses to run until that seeding has happened. Steps over 40 blocks per sample are discarded so teleports cannot pad the total, and bacaphd_lava is zeroed on the grant path.
- **Portal Sniper** — Unchanged this round. Entering the Nether freezes the Overworld anchor AND records the arrival position; every subsequent Nether sample updates bacaphd_ps_far with the furthest the player has been from that arrival point (a running max, not a path length, so milling around next to the portal banks nothing). The return check only grants when bacaphd_ps_far is at least 200 blocks and the Overworld arrival is within 10 blocks of the departure point. This is deliberately not 'link two different portals precisely' - vanilla portal search makes a far-flung second Nether portal land 8x further out in the Overworld, so that version is unachievable. bacaphd_ps_far is reset on the grant path and on every fresh entry.
- **Rainbow Rigging** — Sixteen independent inventory_changed criteria, one per colour-prefixed harness item. requirements_json is empty so the default applies and every criterion name is covered exactly once. Each fires the first time that harness ID appears anywhere in the player's inventory; they do not have to be held at the same time. All sixteen IDs are attested in VALID_IDS.txt.
- **Roof Runner** — FIXED - elytra can no longer bank it at any altitude. The reviewer is right that 'unless block ~ ~-1 ~ minecraft:air' at feet y 128 tests the bedrock roof itself and is therefore always true, so gliding one to five blocks above the roof passed. Two changes replace it: the altitude band is now y 128..129 only (feet on the roof surface, or at the apex of a jump from it - a glider has to stay inside a two-block slot right against the bedrock), and the per-sample step is capped at 6 blocks per half second, i.e. 12 blocks a second. Sprinting is 5.6 and sprint-jumping about 7.1, so foot travel counts in full; unassisted gliding is 15 to 25 and rocket flight 30 plus, so neither contributes anything. The redundant block test under the feet is gone - in the Nether there is nowhere at y 128 except above the bedrock ceiling, which tops out at y 127. - **Breaking Bad** — The brewed_potion criterion is a doorbell, not the completion: requirements are AND-of-groups so holding `brewed` alone can never finish the advancement. bucket_fast sees `brewed=true, impossible=false`, revokes `brewed` first so the very next bottle can ring it again, adds one to bacaphd_brews, and grants at 1000. A fresh counter seeded to 0 at first login, never a lifetime statistic, so it measures brewing done after install. Per-tick sampling is deliberate: brewed_potion fires once per finished bottle pulled off the stand, and a 10-tick sample would drop two of every three-bottle batch.

MECHANISM. One minecraft:entity_hurt_player criterion, so the default requirement set covers it exactly. damage.type.direct_entity must be minecraft:splash_potion (the thrown-potion entity), damage.type.source_entity must be minecraft:player (so a Witch's harming splash does not count), and damage.taken min 1.0 asserts real damage landed. No OR group, no impossible guard.

WHY THIS IDENTIFIES HARMING WITHOUT NAMING IT. A splash potion only appears as the direct entity of damage when the potion's own instant effect does the hurting. Instant Damage is the only such effect that harms a non-undead player: Poison and Wither arrive later as effect damage with no direct entity, and every other splash potion deals none at all. So the splash potion that hurts you is a Potion of Harming. I deliberately did NOT match the potion's contents through the entity's nbt string: the potion_contents component has two serialisations (a bare id and {potion:...}), and an nbt predicate that guesses the wrong one fails silently rather than loudly.

WHAT I VERIFIED, not from memory. minecraft:splash_potion as an ENTITY type is attested repeatedly in BACAP — potion/death_by_magic and monsters/taste_of_your_own_medicine both use killing_blow.direct_entity.entity_type = minecraft:splash_potion. The type/direct_entity + type/source_entity pairing on entity_hurt_player is the shape this pack already ships in weaponry/boomerang_bones. The icon's component shape is copied verbatim from potion/death_by_magic; minecraft:splash_potion, minecraft:potion_contents and minecraft:harming are all in VALID_IDS.txt. The trigger is on the attested list. Parent blazeandcave:potion/death_by_magic ('Kill a mob with a splash potion') is in PARENT_CANDIDATES.md.

TWO DOCUMENTED WEAKENINGS. First, the spare asked for a self-KILL and this grants on being hurt. As with fall damage, minecraft:entity_killed_player needs a killer entity; a self-thrown potion does put the thrower in that slot, but I found no attested case anywhere in BACAP or Enhanced Discoveries of that trigger firing when the victim is their own killer — and the mirror-image trigger explicitly skips the self case (ServerPlayer.awardKillScore guards with 'if entity != this' before firing PLAYER_KILLED_ENTITY), which is exactly the kind of asymmetry that would make it fail silently. I did not gamble a whole advancement on it. The description was reworded to match what is checked.

Second, an advancement cannot compare the thrower's identity to the triggering player's, so source_entity is only narrowed to 'a player'. On a shared server, another player's Splash Potion of Harming would also satisfy it. This is the solo pack (players 1), and the same limitation is already documented for several entries in this project.
- **Have Stand, Will Travel** — Three brewed_potion criteria, all required (default AND). BACAP potion/medic attests the trigger; the dimension rides in the standard entity_properties + location predicate that BACAP nether/midport_village uses. brewed_potion fires when the player takes the potion out of the stand's output slot, so the player is standing at the stand and the location predicate reads the dimension the stand is in.

The three do not have to land at the same time, which matches the wording of the idea - a Witch picks its potion by range and by your health, so collecting all three is a matter of fighting one at several distances.
- **Mise en Place** — One inventory_changed with three item predicates in the `items` list; vanilla requires every entry in that list to be satisfied, and `count` is matched against a single stack's size (the form ED's 'So Bright' uses for 64-count diamonds), so this is three full stacks held simultaneously. - **Net Zero** — Pure criteria. killing_blow.tags is_player_attack is the melee test (same shape as blazeandcave:monsters/lancelot); the effects map requires Strength at amplifier 1 or better (Strength II) and Weakness simultaneously; the empty hand is the inverted equipment.mainhand.count.min=1 idiom already shipped in bacaphd:challenges/naked_and_afraid -- an empty stack has count 0, so the inversion holds only for a truly bare hand. Amplifier is a minimum rather than exactly 1, so Strength III from a beacon stack also qualifies; the gimmick is the same either way.

<details><summary>How these are detected</summary>

- **Around the Clock** — Eight placed_block criteria in two OR groups, ANDed. The first group is the clock loop: place a Hopper whose facing state points at a neighbouring Hopper whose facing points straight back - one criterion per horizontal axis direction. The second group is the readout: place a Comparator whose back (the side opposite its facing) is against a Hopper. The offsetX/offsetZ form on location_check is the same one blazeandcave:biomes/pale_in_comparison uses. No region scan and no function; the two halves are proved by the acts of placing them, so a player could in principle place the Comparator against a different Hopper than the clock's - acceptable slack at task tier.
- **Assembly Line** — DETECTOR 2 of 3. Every five seconds an ungranted non-spectator runs a fixed nine-block line scan anchored on the block they are STANDING ON, which must be the first Crafter: Crafter, Hopper, Crafter, Hopper, Crafter, Hopper, Crafter, Hopper, Crafter, tested in all four horizontal directions (four chained executes, no region scan, no recursion). The pattern is palindromic so standing on either end of the line works. `if items block ~2 ~ ~ container.* *` on the second Crafter is the liveness test: it only passes once material has actually travelled through the first Hopper into the next machine, so a decorative row of blocks does not count, and because the scan repeats every five seconds a chain that is momentarily empty between crafts still passes on a later sample. Stated plainly: block facing is NOT verified. A Crafter's orientation is a compound blockstate and a strict facing test would reject perfectly good builds, so the check is geometry plus proven contents rather than a proof of redstone direction.
- **Cannonball** — REWORKED into an impossible-gated advancement, the shape Enhanced uses for end/dragon_blitz. The `cannonball` criterion is the same fall_after_explosion / TNT cause / distance.horizontal.min 100 as before, now with the same is_flying:false glide guard as Wind Rider; the second criterion is minecraft:impossible and requirements are [["cannonball"],["impossible"]], so the advancement can never complete on its own. Survival is no longer tested inside the criterion, because it cannot be: fall_after_explosion is fired from checkFallDamage BEFORE the landing damage is applied, and the health-criterion objective is only rewritten later in the same player tick, so at criterion time bacaphd_health still holds pre-landing health either way. Instead a bucket_fast line matches `advancements={bacaphd:redstone/cannonball={cannonball=true,impossible=false}}` and runs detect/cannonball. #minecraft:tick functions run at the top of tickChildren, before the levels tick, so that line first sees the completed criterion on the tick AFTER the landing -- by which point bacaphd_health has been rewritten with the post-landing value. 1 or more grants the whole advancement (`advancement grant @s only` completes the impossible criterion too); 0 revokes it, which re-arms the criterion for the next attempt. Once granted, impossible=true and the selector stops matching, so the line self-retires.
- **Chain Reaction** — DETECTOR 3 of 3. The batch's suggested mechanism cannot work: minecraft:target_hit only fires for the player who owns the projectile, and a dispenser-fired arrow has no player owner, so the second and third hits would never trigger anything. Instead the player's own opening shot IS a real target_hit criterion; detect/chain_reaction_arm revokes it again (the pack's existing soul_speed_demon revoke-to-re-prove idiom) and opens a six-sample window, and detect/chain_reaction walks a 13 x 5 x 13 box every bucket_medium tick counting Targets that are powered (`if block minecraft:target` AND `unless block minecraft:target[power=0]`) and Dispensers, granting at three of each. An arrow leaves a Target powered for 20 ticks, comfortably longer than the 10-tick sample, so a real relay is always caught mid-chain. Known cheese: three simultaneous manual hits next to three dispensers would also pass. requirements is AND-of-groups so first_shot alone never completes it.
- **Circular Reasoning** — One detect function, dispatched from bucket_slow through @r so at most one candidate player is scanned per five seconds no matter how many lack it - the same bounded-region-scan discipline the pack already uses for Sorting Facility, Clock Tower and Monochrome. It tests every 2x2 flat Observer ring whose origin falls in the 3x3 footprint at the player's feet level or one block below, in both rotational senses: 36 short-circuiting `if block` chains, each demanding four minecraft:observer blocks whose facing values chain head to tail round the square. Testing both senses is deliberate insurance: whichever way the vanilla `facing` state is read (the observed face or the output face), one of the two patterns is the real working ring, so the check is correct either way. It does mean an anticlockwise ring and a clockwise ring both count, which is right anyway - both are working clocks.
- **Clock Tower** — FIXED - the reviewer's exploit build (a lever on a bell, a detector on the ground and eight dust sprinkled five blocks away) no longer passes, because the check is now vertical. The scan volume changed from 11x7x11 to 9x11x9 - narrower horizontally, much taller - and the loop's own y index doubles as an altitude reading: bacaphd_ct_by keeps the lowest layer holding a powered Bell and bacaphd_ct_dy the highest layer holding an EMITTING Daylight Detector. The grant needs a powered Bell, an emitting Detector, eight pieces of redstone dust / repeaters / comparators in the volume, and the Detector at least five layers ABOVE the Bell. A flat one-room build cannot produce that separation, and a two-block Detector-on-Bell stack certainly cannot; what can is an actual tower with the sensor on the roof and the bell below it, which is what the advancement is named after. It still cannot follow the wire from one end to the other - no command can - and the description now states exactly the three things that are measured rather than implying a timed circuit. The selector carries gamemode=!spectator,gamemode=!creative and every counter is reset at the top of each scan; the two altitude registers are seeded to 99 and -99 so a missing Bell or Detector yields a negative separation and fails.
- **Copper Counter** — Unchanged this round. A 13x5x13 slow-bucket scan around one candidate player counts Copper Bulbs in all eight oxidation and waxed variants, split by their lit blockstate; sixteen bulbs in total with at least four lit and at least four unlit grants it. The mixed pattern stands in for 'working counter', which is not something a command can verify. The air short-circuit skips air, cave_air and void_air, so empty space costs three checks instead of the full sixteen-variant test. The selector carries gamemode=!spectator,gamemode=!creative, and all three counters are reset at the top of every scan.
- **Entrapment** — DETECTOR. Once every 5 s one candidate player (@r, the bounded pattern redstone/sorting_facility already uses for its 16x7x16 scan) has a 16x4x16 volume around them counted for minecraft:tripwire[attached=true] and minecraft:tripwire_hook[attached=true] - attached=true is what 'armed' means, and it is the same state BACAP redstone/tripping_over keys on. It grants at 32 armed wire blocks and 16 armed hooks, i.e. eight complete hook-to-hook runs of at least four blocks each. - **Weapon Rack** — DETECTOR 4. bucket_slow (every 100 ticks) for a player who lacks the advancement and has an item_frame within 12 blocks; bacaphd:detect/weapon_rack clears seven global flags then runs 25 selector tests of the form @e[type=minecraft:item_frame,distance=..12,limit=1,nbt={Item:{id:...}}] — the exact selector form already used elsewhere in this pack for a framed filled_map — covering all seven tiers of sword, axe and spear plus bow, crossbow, trident and mace. All seven flags set in the same pass grants. The flags are recleared every run, so an emptied frame stops counting. Glow Item Frames are not accepted, only Item Frames.
- **Yeet** — minecraft:player_hurt_entity is used purely as an arming pulse, ANDed against an impossible guard in two separate requirement groups so it can never complete on its own. Five gated bucket_fast lines do the arming with no function at all: they tag the nearest non-player, non-item, non-projectile entity within six blocks as bacaphd.yeet, store the player's block X and Z as the anchor, open a 200-tick window and then revoke the `smack` criterion so the next hit can re-arm. The single detect function then runs each tick while the window is open, reads the position of the furthest bacaphd.yeet-tagged entity (`limit=1,sort=furthest`), runs the delta through the shared step helper and grants at 100 blocks or more from the anchor. The delta is pre-seeded with the anchor itself, so if the mob has despawned or unloaded the failed `data get` leaves a zero displacement rather than a stale one. Wind Burst mace smashes and Knockback V sprint hits off a cliff are the practical routes. Attribution caveat: the tag goes on the nearest eligible mob at arm time, which is normally the one you just hit, but a tighter link is not available from the criterion.
